How this is handled

Seven things that are not obvious from the expressions alone.

The window filter is per metric, not globalEach metric filters on its own date column, shown in grey under every expression. There is no single cohort date. One order can land in Q4 for M1, Q1 for M4 and Q2 for M10.
The grain changes twiceOrder grain first. Then one row per metric event, because one order can lose several slots and each loss carries its own date. Then one row per event per column it belongs to.
Distinct counts are not pre-aggregatedM2, M6, M7 and M9 count patients. How many distinct patients fall in a window depends on the window, so the dedup happens at read time. The event row carries the patient id in a unit column and the rendering layer runs COUNT DISTINCT on it.
asof comes from the dataMAX(order_request__created_date) over all rows, never the system clock. Same inputs give the same outputs on any day. It is recorded in every output file, and it is what splits M4 from M5.
The fan out is deliberateEach event is emitted once per column it belongs to, so a date filter in the BI layer is a filter rather than a recompute. One order produced 9 events and 36 rows in the worked case.
Nulls are kept, not droppedAn event whose own date column is null still exists. It goes to an Undated bucket rather than being discarded, because missingness correlates with outcome. Dropping them biases every period column optimistic.
M3 has a fallback chainThe two LTD tables first. If absent, walk the order snapshot history and derive the same thing with LAG. If that is absent too, a boolean flag on the order table. Which source ran is printed and recorded in the run metadata.

Notes for a port

Everything above is expressible in SQL. The two that look procedural are not: the 7 day rule becomes a LAG over the snapshot history if the LTD tables are ever unavailable, and the tier assignment is a RANK. Current implementation is Python, pandas and numpy only, one command end to end, roughly two minutes on ~2,300 orders.

The cross-implementation check is the natural migration test. Move one metric at a time and compare against the existing output before moving the next.

Three rules are not settled with the business yet. Whether a change with RESCHEDULED_CATEGORY = 'Moved Up' counts, which is roughly half the M3 population. Whether M3 counts rows or distinct ORDER_ID. And a third benchmark tier that has no source column anywhere, so it cannot currently be derived. Each is a single named constant.
